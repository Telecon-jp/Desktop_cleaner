# 黑色方块 bug：根因与修复（最终结论）

> **状态：根因已查明，修复已在故障机上通过 8 次重启验证。**
> 本文档已多次修订。早期两个版本分别把「正号索引漂移」和「AND 掩码」
> 当作根因——前者是纯粹的错误推断，后者是不完整的原因。详见第六节。

---

## 一、根因（一句话）

**只要设置了 `Shell Icons\29`（快捷方式箭头的图标替换值），
Explorer 就可能把箭头叠加层渲染成实心黑色方块——与指向哪个图标文件无关。**

因此「换一个更透明的图标」解决不了这个问题。

另一条路是删除 `lnkfile\IsShortcut` —— 它确实能消除黑块，**但会破坏任务栏固定功能**。
两条路都有代价，程序的选择见第三节。

---

## 二、实测矩阵（决定性证据）

对每一种注册表取值，**连续重启 explorer 6 次**，每次截屏统计 48×48 纯黑块数量：

| `Shell Icons\29` 的值 | 6 次重启的结果 | 判定 |
|---|---|---|
| **不设置**（Windows 默认） | `[0, 0, 0, 0, 0, 0]` | **稳定正常** ✅ |
| 自建透明 ICO（AND 掩码全 1） | `[0, 30, 30, 29, 30, 30]` | 基本都黑 ❌ |
| `shell32.dll,-50` | `[0, 30, 30, 30, 30, 30]` | 基本都黑 ❌ |
| `shell32.dll,50` | `[30, 30, 30, 30, 30, 30]` | **100% 黑** ❌ |
| **删除 `lnkfile\IsShortcut`** | `[0, 0, 0, 0, 0, 0]` | **稳定正常，且箭头消失** ✅ |

### 这组数据说明什么

1. **黑块与图标文件内容无关。** 即使换成一个逐像素验证为全透明、AND 掩码正确的
   ICO，甚至换成系统自带的 `shell32.dll,-50`，黑块照样出现。
2. **黑块与「是否设置 29」强相关。** 只要这个值存在，黑块就会出现；
   删掉它，黑块立刻稳定消失。
3. **结果具有随机性。** 同一个值连续重启会在 0 与 30 之间跳——这是竞态/时序问题：
   Explorer 在某些启动时序下加载替代图标失败，并把「黑色占位」写进图标缓存，
   之后就会持续显示黑块（重启也不自愈，因为缓存会写回磁盘）。
4. **正号索引最糟糕**，100% 复现——这正是 v1.0 的原始写法，也解释了
   为什么用户和同学会遇到这个问题。

---

## 三、`IsShortcut` 方案：黑块没了，但代价是任务栏

Explorer 判断「是否为快捷方式绘制箭头叠加层」的依据是
`HKEY_CLASSES_ROOT\lnkfile` 下的 `IsShortcut` 值。删除它之后 Explorer
根本不会请求箭头图标，因此黑块消失 —— 实测 8 次连续重启：
`[0,0,0,0,0,0,0,0]`。

**但这个方法有已知副作用，而且是功能性的**：

> 删除 `IsShortcut` 后，Windows 不再把 `.lnk` 识别为快捷方式，导致
> **「固定到任务栏」「拖拽到任务栏」「收藏夹链接」等功能失效**。
>
> 依据：[Mynavi Windows 专栏](https://news.mynavi.jp/article/windows-121/)
> （该文标题即「**不引发故障**地禁用快捷方式箭头」，正文明确列出上述故障）。
> 本项目使用者也**实际遇到了任务栏固定功能被破坏**，需恢复注册表并注销才复原。

### 两套方案的取舍

| | 方案 A：替换 `Shell Icons\29` | 方案 B：删除 `IsShortcut` |
|---|---|---|
| 黑块 | 可能出现（本机实测必现） | 不会 |
| 系统功能 | **不破坏** | **破坏任务栏固定等** |
| 问题性质 | 纯外观 | 功能损坏 |
| 撤销 | 立即 | 需注销/重启 |

**结论**：方案 A 的失败模式（难看但可用）明显优于方案 B 的失败模式（好看但功能坏）。
因此程序默认用 A，B 降级为需用户明确勾选的选项。

**教训**：我当初只验证了「黑块消失」这一个指标就宣称方案 B「可靠」并推荐给用户，
没有排查它的副作用。**验证一个方案时，必须同时检查它是否破坏了别的东西。**

## 四、修复内容

`desktop_cleaner.py`：

1. **`remove_shortcut_arrow()` 默认用方案 A（图标替换）** —— 不破坏系统功能；
   方案 B 由 `_remove_arrow_by_isshortcut()` 实现，仅当 `use_isshortcut=True` 时调用，
   并在文档串与界面中明确标注副作用。
2. **`remove_both()`**：箭头默认走方案 A，盾牌走 `Shell Icons\77`
   （盾牌没有等效机制，只能替换图标）。
3. **`restore_defaults()`**：删除 `29`/`77` + 重建 `IsShortcut`，一键兜底。
4. **`repair_stale_icon_cache()`**：移除黑块来源（删 29）并把箭头还原为系统默认
   —— 不再走 IsShortcut 那条会破坏功能的路。
5. **启动自检**：检测到 `29` 已设置时提示黑块风险；检测到 `IsShortcut` 缺失时
   提示任务栏风险。
4. **`repair_stale_icon_cache()`**：针对「注册表和文件都正确但仍有黑块」的
   情况，强制重建图标缓存。
5. **`_atomic_write()`**：ICO 改为原子写入，避免 Explorer 读到写了一半的文件。
6. `ensure_transparent_ico()`：内容已正确时不再重写文件（避免无谓改动时间戳）。

GUI：

- 「去除快捷方式箭头」卡片改用推荐方案，并说明不会产生黑块；
- 原「兼容模式」勾选项改为「去箭头时使用旧方案」，默认不勾；
- 新增「修复黑色方块（保留去箭头）」按钮。

## 五、验证工具

`detect_blackbox.py`：最小化所有可见窗口（记录句柄，测完恢复）→ 截屏 →
连通域分析找出 40–56px、填充率 >0.98 的纯黑矩形 → 与桌面 `SysListView32`
的实际图标坐标比对，只统计落在图标位置上的。

`matrix_test.py`：对指定的注册表取值连续重启 explorer N 次并统计黑块数，
用于判断某项配置是「稳定正常 / 稳定黑块 / 时好时坏」。

`probe_blackbox_cause.py`：分步骤测量（初始 / 只重启 / 清缓存+重启 / 再只重启），
用于定位问题发生在哪一步。

## 六、两次错误结论的记录

### 错误一：正号索引漂移（已推翻）

**结论**：黑块是 `shell32.dll,50` 的正号索引漂移到「无 alpha 通道的老式图标」造成的。

**错在哪**：依据仅仅是「本机 `ExtractIconEx(shell32.dll, 50)` 恰好返回透明图标」，
就编出了一套解释。实际上根本没有检查真正的合成路径。

### 错误二：AND 掩码（不完整）

**结论**：黑块是自建 ICO 的 AND 掩码填了全 0 造成的（AND=0 表示不透明，
于是画出 XOR 的纯黑）。

**这个发现本身是对的**——AND 掩码全 0 确实会独立造成黑块。
但它**不是**用户遇到的那个问题的原因：把 AND 掩码修正为全 1 之后，
黑块依然出现，因为真正的触发条件是「设置了 `Shell Icons\29`」这件事本身。

### 共同的方法论错误

两次都犯了同一个毛病：**用一个中间产物的性质，去论证最终渲染结果**。
第一次是「图标文件的 alpha」，第二次是「图标文件的 AND 掩码」。

**最终能定位问题，靠的是三件事**：

1. **把判定量化**——写出 `detect_blackbox.py` 直接数黑块，而不是肉眼看；
2. **做受控的重复实验**——连续重启 6 次才发现结果会「跳动」，
   如果只测一次，就会把随机结果当成必然规律（我前期正是如此）；
3. **建立对照组**——「不设置 29」这一组永远是 0，是最关键的基准线，
   正是它把矛头从「图标文件」转向了「设置 29 这个动作本身」。

**教训**：当现象具有随机性时，单次实验毫无意义；必须重复足够多次，
并始终保留一个已知正常的对照组。

**更重要的教训：验证维度不能只有一个。**
方案 B（`IsShortcut`）在「黑块」这个指标上满分，却破坏了任务栏固定功能。
我只测了前者就宣称它「可靠」并推荐给用户，导致使用者实际受损。
**换方案时要问：它有没有弄坏别的东西？**
