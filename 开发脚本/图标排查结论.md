# 黑色方块 bug：根因与修复（最终结论）

> **状态：已定位、已修复、已在故障机上实测验证。**
> 本文档替代早期版本。早期版本把「正号索引漂移」当作根因，那是**错误的推断**，
> 现已在第六节记录该错误。

---

## 一、根因（一句话）

**自建 ICO 时把 DIB 的 AND 掩码平面填成了全 0，导致 Explorer 把叠加层画成实心黑块。**

修复：**AND 掩码填全 1（0xFF）**。这是一处每平面 128 字节的改动。

---

## 二、原理

DIB 格式的图标由两个位平面组成：

| 平面 | 内容 |
|---|---|
| XOR | 彩色像素 + alpha 通道（32bpp） |
| AND | 1bpp 掩码，按**经典合成规则**参与运算 |

经典合成规则：

```
AND=1, XOR=0   ->  透明（露出背景）
AND=0, XOR=x   ->  不透明，画出 x 的颜色
```

出问题的实现写的是：

- `XOR = 全 0` → 颜色是**纯黑**，alpha 也是 0；
- `AND = 全 0` → 按上表 = **不透明**，于是画出 XOR 的纯黑。

**结果 = 一个 48×48 的实心黑色方块。**

关键点：`alpha=0` 只在**支持 alpha 的合成路径**下表示透明。
Explorer 绘制**叠加层**（快捷方式箭头就是叠加层）时常常走**经典掩码路径**，
此时 alpha 被忽略，只看 AND 掩码——于是黑块出现。

这解释了全部现象：

- 为什么黑块**恰好出现在箭头的位置**（就是叠加层）；
- 为什么黑块是**图标单元大小**的实心矩形；
- 为什么「把 alpha 写成 0」看起来天经地义却没用。

## 三、实测对照（受控实验）

每轮实验流程相同：设置 `29` → `taskkill explorer` → 清空全部 `iconcache*.db`
→ 重启 explorer → 最小化窗口 → 截屏 → 按图标网格统计 48×48 纯黑块。

| # | `29` 的值 | 黑块数 | 箭头 |
|---|---|---|---|
| A | （删除，Windows 默认） | **0** | 在 |
| B | `C:\Windows\System32\shell32.dll,-50` | **0** | 已去除 |
| C | 自建 ICO，AND 掩码全 **0**（单档 32×32） | **30** | 已去除 |
| D | 自建 ICO，AND 掩码全 **0**（10 档多尺寸） | **30** | 已去除 |
| E | Pillow 生成（内部为 PNG 格式） | **0** | 已去除 |
| F | `shell32.dll,-50`（重测，确认可复现） | **0** | 已去除 |
| G | **自建 ICO，AND 掩码全 1（修复后）** | **0** | 已去除 |

结论：

1. 黑块与 **AND 掩码**强相关，与图标尺寸档数、文件路径无关；
2. Pillow 生成的 ICO 不带黑块，是因为 **Pillow 把像素存成 PNG** 而非 BMP/DIB，
   走的是 alpha 合成路径，绕开了 AND 掩码问题；
3. `shell32.dll,-50` 不带黑块，是因为系统资源里的图标格式本来就是正确的。

### 为什么「多尺寸」不是原因

早期曾怀疑「ICO 只有 32×32 单档，缩放到 16×16 时丢 alpha」。
实验 D 用 10 档多尺寸 ICO（16/20/24/32/40/48/64/96/128/256）复测，
**黑块数依然是 30**，该假设被排除。

## 四、验证工具

`detect_blackbox.py` 是本问题的专用测量工具，避免了「靠肉眼看截图」的不确定性：

- 通过 `EnumWindows` 最小化所有可见顶层窗口（并记录句柄，测完恢复）；
- 截屏后用连通域分析找出所有 **40–56px、填充率 > 0.98** 的纯黑矩形；
- 与桌面 `SysListView32` 的实际图标坐标比对，只统计落在图标位置上的黑块
  ——这样即使有窗口遮挡或壁纸本身有黑色区域也不会误报。

用法：

```
python 开发脚本\detect_blackbox.py [输出截图.png]
```

退出码 0 = 无黑块，1 = 存在黑块。

## 五、修复内容

`desktop_cleaner.py`：

1. `build_transparent_ico_bytes()`：AND 掩码由 `b"\x00"` 改为 `b"\xFF"`；
2. `verify_transparent_ico()`：校验逻辑同步反转，改为断言 AND 掩码**必须全为 0xFF**
   （旧的校验器会把这个 bug 判为「通过」，属于同源错误）；
3. 相关注释、GUI 文案、模块文档串全部更新为已验证的结论。

`test_v2_selfcheck.py`：新增针对 AND 掩码的**回归测试**，
断言 128 字节全部为 `0xFF`，防止该 bug 再次引入。

## 六、早期错误结论的记录与教训

**错误结论**：黑块是「正号索引 `,50` 漂移到无 alpha 通道的老式图标」造成的。

**它错在哪**：该推理的依据只是「本机 `ExtractIconExW(shell32.dll, 50)` 恰好返回透明图标」。
仅凭这一点就编出了一套「索引漂移」的解释，并写进了代码注释和文档。
实际上黑块的真因（AND 掩码）当时完全没有被检查过。

**更严重的错误**：用「我生成的图标 alpha 全为 0」去论证「我的修复有效」。
这是**循环论证**——它只证明了图标文件本身的性质，没有证明最终渲染结果。
因此那个「修复」上线后，在故障机上黑块依旧，浪费了用户的时间。

**教训**：

1. 涉及「渲染结果」的问题，只能以**最终渲染结果**为验证标准，不能用中间产物的性质替代；
2. 验证必须**可量化、可复现**（因此写了 `detect_blackbox.py` 做黑块计数），
   不能依赖「看起来没问题」；
3. 要主动寻找**反例实验**。本次正是靠「换成 Pillow 生成的 ICO 就没有黑块」
   这一对照组，才把范围从「独立 ICO 文件」缩小到「我生成的字节格式」。
